# 1015_05 지표 교차 검증

- 상태: 확정 (사용자 결정, 2026-10-15). 대조 지표 5개 모두, 일치 기준은 완전 일치
- 코드: `src/cross_check.py` → `outputs/cross_check.csv`
- 배경: AGENTS.md 규칙 "지표는 pm4py와 다른 방법(pandas·SQL)으로 다시 계산해 대조한다. 같은 코드를 다시 돌리는 것은 검증이 아니다", 로드맵 완료 조건 "핵심 지표 3개 이상을 두 방법으로 계산해 일치"

## 1. 결정할 것과 선택지

### 대조 범위

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 5개 모두** | 직접 이어짐, 구간 관찰 대기, 대기 단계, 묶음 처리, KM 중앙값 | 보고서의 핵심 수치가 모두 두 방법으로 확인된다. 특히 KM은 직접 짠 함수라 검증이 가장 필요하다 | 코드가 길어진다 |
| B. 최소 3개 | 로드맵 완료 조건만 충족 | 빠르다 | 보고서에 쓰는 수치 중 검증 안 된 것이 남는다(예: KM 531일) |

### 일치 기준

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 완전 일치** | 건수는 같아야 하고, 중앙값·분위수·KM 중앙값도 같은 정의라면 같아야 한다(소수점 오차 1e-9만 허용) | 정의가 같으면 결과가 같아야 한다는 원칙에 맞다. 작은 차이도 원인을 찾게 된다 | 정렬·빈 값 처리 같은 작은 차이도 실패로 잡힌다 |
| B. 허용 오차(예: 1%) | 조금 달라도 통과 | 통과가 쉽다 | 버그가 오차 안에 숨는다. 이번에 찾은 회의일 2건 차이(0.8%)는 B였다면 통과했다 |

### 결정: 범위 A(5개 모두) + 기준 A(완전 일치)

- 근거 1: 보고서 핵심 결론(소위 상정 대기 KM 531일, 묶음 99.7%, 계류 9,667건)이 모두 대조 대상에 들어간다
- 근거 2: 날짜가 일 단위 정수라, 같은 정의라면 중앙값까지 정확히 같아야 한다. 허용 오차를 두면 정의 차이·버그를 놓친다
- 근거 3: 직접 구현한 KM 함수는 라이브러리 검증이 없어, 전혀 다른 방식(SQL 창 함수와 로그 합)으로 다시 계산해야 믿을 수 있다

## 2. 방법: 무엇이 "다른 방법"인가

| 지표 | 기존 계산 | 다시 계산 | 무엇이 독립적인가 |
|---|---|---|---|
| ① 직접 이어짐 빈도·대기 중앙값(51개 연결) | pm4py `discover_dfg`·`discover_performance_dfg` | DuckDB `LEAD()` 창 함수 | 라이브러리 내부 구현 대 SQL |
| ② 구간 관찰 대기(11개 구간: 건수·중앙값·90분위) | pandas `pivot_table` | SQL 자기 조인 + `median`·`quantile_cont` | 집계 코드 전체 |
| ③ 진행 중 의안의 대기 단계(11개 단계: 건수·경과 중앙값·90분위) | pandas `apply`(파이썬 함수) | SQL `row_number()` + `CASE` | 마지막 이벤트 선택과 단계 분류 규칙을 새로 작성 |
| ④ 묶음 처리(6개 값) | pandas `groupby.transform` | SQL `count() OVER (PARTITION BY …)` | 그룹 집계 |
| ⑤ KM 중앙값(11개 구간) | 직접 짠 파이썬 함수(`cumprod`) | SQL: 위험 집합 `sum() OVER (ORDER BY t DESC)`, 생존확률은 `ln` 누적합의 `exp` | 알고리즘 표현 자체가 다름(곱 대 로그 합) |

- 두 계산이 공유하는 것은 **입력(이벤트 로그 CSV)과 정의(1015_03·1015_04)뿐**이다. `cross_check.py`는 `analysis.py`를 불러오지 않는다
- 정의가 공유되므로 이 검증은 "정의를 코드로 옮길 때의 실수"를 잡는다. 정의 자체가 맞는지는 화면 대조(1015_01·03)와 민감도 점검(1015_03)이 맡는다
- 추가 확인: CSV 행 순서가 (의안, 날짜, 절차 순서) 정렬과 같은지(직접 이어짐은 행 순서에 의존하므로)

### 처음 실행에서 어긋난 것 1개 → 분석 코드 버그였음

| 항목 | pandas | SQL | 원인 | 조치 |
|---|---|---|---|---|
| 소관위 처리가 일어난 (위원회, 날짜) 수 | 242 | 244 | 위원회 이름이 비어 있는 소관위 처리 2건(2200168 회송, 2206564 원안가결). pandas `groupby`는 기본값(`dropna=True`)으로 빈 값 그룹을 빼고, SQL은 빈 값도 한 그룹으로 센다 | `analysis.py`·`figures.py`에 `dropna=False`. 다시 실행해 244로 바로잡고 1015_04 결과 수정 |

- 영향: 두 건 모두 혼자 처리된 경우라 묶음 비율(99.7%)·묶음 크기 중앙값(41건)은 그대로. 묶음 크기 표의 "1건" 칸이 16 → 18, 회의일 수가 242 → 244로 바뀜
- 기준을 허용 오차(1%)로 했다면 통과해 버그가 남았을 것이다

### 그 밖에 알게 된 것

- 이벤트 로그 CSV의 소위원회 이름 1건에 줄바꿈 문자가 들어 있다(원본 값). DuckDB가 따옴표 규칙을 자동 감지하지 못해 읽기에 실패했고, 따옴표를 명시해 해결했다. pandas는 표준 CSV 규칙으로 읽어 문제가 없었다
