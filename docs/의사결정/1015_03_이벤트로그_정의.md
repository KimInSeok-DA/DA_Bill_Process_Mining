## 2. 결정별 근거

결정마다 "확인한 것 → 다르게 정하면 생기는 문제 → 바꾸는 조건"으로 적는다. 수치는 2026-10-15 수집분을 pandas와 DuckDB SQL(원본 JSON 직접 읽기)로 각각 계산해 같은 값임을 확인했다.

### 2-1. 진행 중 의안을 넣는다

| 확인한 것 | 값 |
|---|---|
| 제안 분기별 처리 비율 | 2024년 2분기 45% → 2025년 4분기 24% → 2026년 2분기 5% |
| 처리된 의안만 본 소관위 상정 → 처리 중앙값 | 33일 (5,288건) |
| 소관위 상정 뒤 아직 소관위 처리도 최종 처리도 없는 의안 | 11,242건(상정 의안 16,535건의 68%), 상정 뒤 경과 중앙값 402일. 1년 넘은 의안 5,966건(36%) |

- 다르게 하면: 처리된 의안만 넣으면 "소관위는 한 달이면 처리한다"가 되지만, 실제로는 상정 의안의 68%가 아직 처리 전이다. 끝까지 관찰하지 못한 대상을 빼서 생기는 왜곡(중도절단, right censoring)이고, 이 프로젝트의 질문("어디서 멈추나")에 반대 답을 낸다
- 분석 때: 지표를 "처리된 의안 기준"과 "조회일까지 경과 기준"으로 나눠 보인다
- 바꾸는 조건: 없음

### 2-2. 끝 활동을 결과별로 나눈다

| 결과 | 건수 | 법사위 거침 | 소관위 처리 있음 | 제안→처리 중앙값 |
|---|---|---|---|---|
| 대안반영폐기 | 4,308 | 0 | 4,308 | 205일 |
| 수정가결 | 533 | 495 | 533 | 203일 |
| 원안가결 | 193 | 169 | 185 | 167일 |
| 철회 | 171 | 0 | 27 | 15일 |
| 수정안반영폐기 | 39 | 0 | 39 | 245일 |
| 폐기 / 부결 | 4 / 1 | 0 / 1 | 4 / 1 | — |

- 다르게 하면: 끝을 "본회의 의결" 하나로 두면 사실과 다르다. 대안반영폐기·수정안반영폐기 4,347건은 원안이 본회의에 가지 않고, 철회 171건은 표결이 없다. 경로 지도에서도 결과별 갈림이 사라진다
- 원안·수정을 합치는 이유: 둘 다 법사위를 거치는 비율이 87～93%로 같은 절차다. 차이는 내용 수정 여부라 속성으로 충분하다
- 바꾸는 조건: 원안·수정 사이의 소요 기간 차이가 분석 질문이 되면 나눈다

### 2-3. 대안반영폐기는 소관위 처리와 끝 활동을 둘 다 넣는다

- 확인한 것: 4,347건 모두 두 날짜가 있다. 위원회 처리 → 대안 본회의 통과 중앙값 22일(사분위 8～50일), 같은 날 55건(1.3%), 역전 0
- 다르게 하면: 위원회 처리에서 끝내면 이 22일이 사라지고, 본회의에서 끝나는 가결 의안과 전체 소요 기간을 같은 기준으로 비교할 수 없다
- 미처리인데 소관위 결과가 대안반영폐기인 174건: 위원회 처리 뒤 중앙값 218일째 대안을 기다리는 중 → "소관위 처리"까지 넣고 진행중으로 둔다

### 2-4. 같은 날은 절차 순서로 정렬한다(필수)

- 확인한 것: 의안 날짜만으로도 1,918건(9.6%)에 같은 날 인접 단계가 있다(소관위 상정 = 처리 1,219건 등). 소위까지 보면 소위 상정 = 처리 2,988건
- **pm4py는 같은 시각이면 입력 행 순서를 따른다**(직접 실험: 같은 날 두 활동의 행 순서만 바꾸자 흐름이 A→B에서 B→A로 바뀜). 그래서 정렬은 선택이 아니라 필수다
- 가짜 시각(+1시간 등)을 넣지 않는 이유: 대기 0일은 사실이다. 정렬 순서 열(`step_order`)만 둔다

### 2-5. 소위 기록이 여러 줄이면 줄마다 넣는다

| 여러 줄 의안 471건 | 의안 |
|---|---|
| 회부일이 모두 같음(같은 날 두 줄) | 196 → 합치면 회부 1번 |
| 회부일이 2개 이상 | 271. 그중 251건은 위원회가 바뀜(위원회 개편, 특별위원회 회부·환원) |
| 회부일 없음 | 4 |

- 그래서 반복되는 소위 회부는 대부분 "다시 심사"가 아니라 **위원회 이관에 따른 재회부**다
- 줄마다 넣는 이유: 첫 회부 → 마지막 회부 중앙값 359일. 첫 회부·마지막 처리만 쓰면 이전 위원회에 1년 가까이 머문 사실이 사라지고 한 소위에서 기다린 것처럼 보인다
- 같은 의안·활동·날짜는 하나로 합친다: 소위 회부 3, 상정 45, 처리 45개(합 93)
- 바꾸는 조건: 일정이 밀리면 1015_02대로 단일 행 의안만 넣는다

## 4. 경로에 따른 보정 (이벤트 로그를 만들며 발견)

pm4py로 불러 흐름을 보니 절차를 거꾸로 가는 흐름이 있었다(처음 만든 로그: "소위 처리 → 소관위 상정" 1,028건 등). 원인은 데이터 오류가 아니라 필드의 뜻이 경로마다 다르기 때문이었다.

| 발견 | 확인한 것 | 보정 |
|---|---|---|
| 소위가 먼저 심사한 경로(소위 직접 회부, 국회법 제58조제4항 등)에서는 소관위 상정이 소위 처리 **뒤**에 온다 | 직접 회부 2,267건 중 소관위 상정일이 있는 1,236건의 1,177건이 소위 처리일 이후(998건은 소관위 처리일과 같은 날). 직접 회부 표시가 없는데 같은 경로인 의안도 16건(소위 회부일 없음, 소관위 상정 = 처리) | 소관위 상정일이 첫 소위 처리일과 같거나 늦으면 `step_order`를 6.5(소위 처리 뒤, 소관위 처리 앞)로 둔다(1,242개). 날짜가 다르면 날짜가 순서를 정하므로 같은 날만 영향 |
| 위원회가 바뀐 의안의 `COMMITTEE_DT`는 **새 위원회 회부일**이다 | 301건이 소관위 회부일 > 첫 소위 회부일(251건은 소위 기록의 위원회가 여럿). 회부 월: 2025-10 115건, 2026-07 81건 등. 첫 회부일은 의안 API에 없다 | 이 301건은 활동 이름을 "소관위 재회부"로 둔다. "제안 → 소관위 회부" 대기 계산에서 자연히 빠진다 |

- 1015_01에서 따로 확인하기로 한 "제안 → 회부 30일 초과 465건" 중 301건이 이 재회부였다. 재회부를 나눈 뒤 남은 164건은 분석 단계에서 확인한다

### 남은 역행 흐름 (보정 후)

| 소위 처리 → 소관위 처리 | 2일 (5,123) | 2일 (5,126) |

- 중앙값이 모두 같다. 예외를 빼는 규칙은 지표를 바꾸지 않고, 경로 지도의 거짓 흐름만 없앤다
- pm4py로 불러온 순서 = 저장 순서(19,917 케이스 전부) 확인

## 7. 결정 과정과 고친 것

1. AI가 추천안을 냄 → 사용자: 추천대로 가되 "왜 그렇게 정했는지 근거가 미흡하다"
2. AI가 결정마다 수치 근거를 계산 → 사용자: 전반 재검증 요청
3. 원본 JSON을 DuckDB SQL로 따로 읽어 다시 계산 → AI 설명 2곳이 틀린 것을 발견해 고침
   - "상정 의안의 2/3가 1년 넘게 멈춤" → 실제는 68%가 처리 전, 1년 넘은 의안은 36%
   - "반복 소위 회부의 93%는 위원회 개편" → 개편과 특별위원회 회부·환원이 섞여 있음
4. 예외 5건을 사용자가 화면으로 확인 → 규칙 2개 조정(결과 없는 처리일은 넣지 않음, 철회 규칙을 "철회일과 같은 날"로 좁힘), 활동 이름을 "처리"로 바꿈
5. 이벤트 로그를 pm4py로 불러 흐름을 확인 → 역행 흐름 발견 → 경로별 필드 뜻 차이 2개를 보정(4절)

## 8. 대안과 바꾸는 조건
