# 1015_06 범위 확장: 정부안·위원회안(대안)과 원안-대안 연결

- 상태: 확정 (사용자 결정, 2026-10-15). 결정 1～4 모두 A안
- 코드: `src/collect.py --service allbills|altref`, `src/build_event_log.py`(v2)
- 배경: v1은 의원발의 법률안만 다뤘다. 사용자가 정부제출안·위원회안까지 넣으면 품질에 도움이 될 것이라고 제기했다. 특히 처리된 의원안의 82%(4,308건)가 대안반영폐기인데, 그 의안들을 흡수한 **대안 자체가 데이터에 없어** "원안 → 대안 → 본회의" 경로를 끝까지 보일 수 없었다
- 선택지 표기에 대해: 이 문서의 표는 AI가 추천안을 A에 두고 쓴 것이다. 사용자가 "전부 A가 최선이라 A였던 것 아니냐"고 짚었고, AI는 표 순서가 추천을 반영한다고 답했다. 그래서 각 결정에 B·C안이 더 나은 조건을 "바꾸는 조건"으로 함께 적는다

### 결정 3. 원안-대안 연결

| 안 | 장점 | 단점 |
|---|---|---|
| **A. 원안·대안을 각각 케이스로 두고, 원안에 `alt_bill_no` 속성 + 연결 표(`alt_links.csv`)** | 이벤트가 복제되지 않아 빈도·대기 통계가 정확. 연결 표로 원안의 "소관위 처리 → 대안 본회의" 대기를 대안의 법사위·제출 단계로 쪼갤 수 있음 | 원안과 대안을 이어 보는 분석은 조인으로 따로 해야 함 |
| B. 원안 케이스 뒤에 대안의 이벤트를 이어 붙임 | 원안 하나의 경로가 한 줄로 끝까지 보임 | 대안 1건의 이벤트가 원안 수만큼 복제됨(원안 7건이면 법사위 회부 7번). 경로 지도의 법사위 빈도가 부풀려짐 |
| C. 원안 여러 건 + 대안을 하나의 "묶음 케이스"로 합침 | 묶음 처리(H2)를 직접 표현 | 케이스 정의가 복잡하고, 원안별 대기를 볼 수 없음 |

- 여러 객체가 얽힌 이런 구조를 프로세스 마이닝에서는 객체 중심(object-centric) 문제라고 부른다. A는 이를 "케이스 표 + 연결 표"로 가장 단순하게 다루는 방법이다
- 바꾸는 조건(C가 나은 때): 분석 질문이 "대안 묶음이 어떻게 만들어지나"로 바뀌면, 객체 중심 이벤트 로그(OCEL) 형식으로 원안·대안을 함께 모델링한다

### 결정 4. 위원회안의 제안일

- 화면 C(2221667 해상교통안전법(대안)): 소관위 의결 09-17 → 법사위 회부 09-17·처리 09-28 → **제안일 09-30**(문서 "위원회제출안(체계자구심사 반영)") → 본회의 10-01. 화면 진행 단계도 "접수 09-30 → 본회의 심의 10-01"뿐이다
- 데이터: 위원장 제안 907건에서 제안일은 법사위 처리일과 같거나 늦고(같은 날 652건), 본회의보다 늦은 경우는 0건

| 안 | 장점 | 단점 |
|---|---|---|
| **A. "위원회 제출" 활동으로 법사위 처리 뒤, 끝 활동 앞에 둠(`step_order` 10.5)** | 실제 순서 그대로. 법사위 뒤 제출까지의 대기도 보임 | 활동이 하나 늘어남 |
| B. 원안처럼 "제안"을 첫 활동으로 | 이름 통일 | 날짜상 소관위·법사위보다 늦어 순서가 맞지 않음 |
| C. 쓰지 않음 | 단순 | 법사위 → 본회의 사이의 실제 단계가 빠짐 |
